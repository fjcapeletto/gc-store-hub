# Device Identity & Provisioning — architecture decisions (for the backend)

> **Status: decisions to implement, hub + server.** Wire shapes land normatively in
> `device-authorization.md` / `.schema.json`; this file is the *why* + the DB/flow implications
> for `gc-store-server`. Owner-driven; reflects the model agreed 2026-07-25.

## The core inversion

The **`device_id` is generated by the HUB**, not assigned by the server. The **`license_key`
is issued by the server** out-of-band. They are paired in the DB `device` row, but they enter
that row from opposite sides.

## Two provisioning paths (the two commercial moments)

1. **Factory-installed (we sold the laptop).** At imaging, a provisioning step creates the
   `device` row and bakes both `device_id` and `license_key` onto the machine. The device boots
   already `granted`.
2. **A-posteriori (trial / remote purchase, no prior hardware access).** The machine has no
   access. The user requests it *from inside the hub*; approval issues a `license_key` emailed to
   them; they type it into the hub to activate. **We never touch that machine** — so the
   `device_id` must be produced *on the device* and travel to us in the request.

Path 2 is why `device_id` is hub-side.

## `device_id` construction (hub-side, versioned)

Generated **once**, at request time (path 2) or at imaging (path 1), then **persisted** locally
and reused forever:

```
seed      = high-resolution timestamp (ticks)  +  OS randomness (GUID)  +  hardware anchor
hw anchor = TPM EK public hash  ||  distinctive SMBIOS UUID  ||  distinctive board serial  ||  ProcessorId
device_id = "dev_" + base32( SHA-256( "gcstore-dev-v1|" + seed ) )[:26]
```

Properties:

- **Unique** — the timestamp+GUID guarantee no collision even across machines with junk/shared
  SMBIOS (the "To be filled by O.E.M." case). This is the main thing the timestamp buys.
- **Opaque** — a hash; no MAC/serial/PII in the id, the DB, or the lease `sub`.
- **Persisted** — once generated it does not recompute, so minor hardware drift never changes it.
- **Versioned** — `v1` in the pre-image lets us evolve the algorithm.

### What the timestamp does and does NOT do (be precise)

- It **defeats "regenerate by spoofing hardware"**: machine B can't reproduce A's id because it
  can't reproduce A's exact-millisecond seed.
- It does **NOT** defeat **copying the stored id file** A→B. A persisted id is copyable. So the
  timestamp is a *uniqueness* mechanism, **not** the anti-clone.

## The real anti-clone: fingerprint bound at activation (server-side)

The binding "one license → one machine" is enforced by the **server**, not by the id:

- On the **first successful authorize** with a given `license_key` (activation), the server
  **records the device fingerprint** sent in the claim and pins `device_id + license_key` to it.
- A later authorize carrying the same `device_id`/`license_key` but a **materially different
  fingerprint** ⇒ reject / flag (needs re-endorsement).
- **Tiers** (already agreed): with **TPM**, binding is cryptographically strong (the EK can't be
  copied); **without TPM**, it's the **fingerprint tier** — stops *casual copying*, not a
  *patched client*. That's the untrusted-client ceiling, same as everywhere.
- Fingerprint drift is real (NIC swap, dock, BIOS update) — the server should **soft-match**
  (tolerate partial change), consistent with the hub's existing baseline/scoring model, and route
  gross change to re-endorsement rather than hard-fail.

## The access-request flow (path 2), end to end

1. Machine has no license → hub shows the **offer + a "Request access" form**.
2. User enters **full name + email** (v1). Hub generates+persists `device_id`, then
   `POST /v1/access-request { deviceId, name, email, fingerprint }`.
3. Server stores it as **`requested`**. Owner reviews and **approves/denies manually**.
4. While pending, the hub shows **"Access requested — awaiting approval"**.
5. On approval, the owner (server) **emails the `license_key`** for that `device_id`.
6. User types the `license_key` on the hub's **licensing screen** → hub persists it → next
   `authorize` presents `{ deviceId, license, fingerprint }` → server binds the fingerprint and
   returns a **granted lease** → unlock.

## What the server needs — ALTER the installed schema to the model

The DB already has `customer` / `device` / `device_entitlement`. The business rule (below) drives the
shape; the `device` table just needs to grow to hold the lifecycle. These are **`ALTER`s, not a
rewrite** — and no separate request table (a request is a `device` in state `requested`).

```sql
ALTER TABLE device
  -- a request exists before there's a customer or a license:
  MODIFY  customer_id  BIGINT UNSIGNED NULL,       -- was NOT NULL; linked on approval
  MODIFY  license_key  VARCHAR(128)   NULL,        -- was NOT NULL; minted/issued on approval
  -- carry the full lifecycle in the existing state column:
  MODIFY  access_state ENUM('requested','granted','locked','denied','revoked')
                       NOT NULL DEFAULT 'requested',
  -- requester details captured at request time (before a customer row exists):
  ADD COLUMN req_name  VARCHAR(255) NULL,
  ADD COLUMN req_email VARCHAR(255) NULL,
  -- when the fingerprint was pinned to this device (activation):
  ADD COLUMN bound_at  DATETIME NULL;
-- `fingerprint` (JSON) and `tpm_ek_pub` already exist → the binding lands there.
-- nullable customer_id keeps fk_device_customer (ON DELETE RESTRICT) valid;
-- nullable license_key is fine under uq_device_license_key (InnoDB allows multiple NULLs).
```

### Flow on the (altered) tables

- **A-posteriori — request** → `INSERT device(device_id, access_state='requested', req_name,
  req_email, fingerprint=<advisory>)`; `customer_id` and `license_key` stay NULL.
- **Approve** → mint `license_key`, upsert `customer(email,name)` and set `customer_id`, set
  `access_state='granted'`, insert `device_entitlement` rows, **email the key**.
- **Activation** (first authorize carrying the license) → **pin** the claim's fingerprint onto
  `device.fingerprint` (+ `tpm_ek_pub` when present), set `bound_at`; later authorizes **soft-compare**
  and reject/flag on material change.
- **Factory path** → `INSERT device(customer_id, license_key baked, access_state='granted')` +
  entitlements — same table.
- **Denied / revoked** → `access_state='denied'` / `'revoked'`.

### Hub-side notes for the backend

- The claim's `device_id` **is** `device.device_id` (unique) — the hub generates it, so provision
  against the value the hub shows (its Access panel / `device.json`), not a hand-picked string.
- The hub sends `fingerprint` as a JSON dict of distinctive signals (incl. an `ekHash`) → lands in
  `device.fingerprint`. To populate **`device.tpm_ek_pub` (raw EK)** the hub must send the raw EK in
  `claim.attestation.tpmEk`; today the collector exposes only the EK **hash**, so raw-EK sending is a
  small future enhancement.

## Endpoints (normative shapes in device-authorization.md)

- `POST /v1/access-request` `{ deviceId, name, email, fingerprint }` → `202 { status:"requested" }`
  (or the current status if the `deviceId` already has one).
- `POST /v1/authorize` — the claim now also carries **`deviceId`** and **`fingerprint`**; a device
  with a pending request but no license gets `403 { reason:"access-pending" }`.
